This blog was running Next.js 15.3.8. Next.js 16.3.1 is out, so I upgraded it. Two things broke, and three dependency bumps turned out to be worth refusing. Here's the whole thing, including the parts that were boring.

## The Starting Point

The site is an App Router portfolio and blog:

- MDX posts compiled by `@next/mdx`, with `remark-frontmatter` for YAML and `rehype-pretty-code`/Shiki for syntax highlighting
- Tailwind CSS v4, `next-themes` for light/dark, shadcn/ui on Radix primitives
- A hand-rolled ESLint flat config, Husky + commitlint + lint-staged on commit
- No test runner — the build and the browser are the verification

Worth noting up front: most of the well-publicised Next 16 breaking changes didn't apply here. `params` was already typed `Promise<{ slug: string }>` and awaited. No middleware, no parallel routes, no `unstable_*` APIs, no AMP. If you kept up with the Next 15 async-request-API migration, you've already done most of the work.

## What Broke #1: Turbopack Can't Serialize Your MDX Plugins

Turbopack is the default bundler in Next 16 for both `dev` and `build`. The first build failed immediately:

```
Error: loader /node_modules/@next/mdx/mdx-js-loader.js for match "{*,next-mdx-rule}"
does not have serializable options. Ensure that options passed are plain JavaScript
objects and values.
```

The cause is in `next.config.ts`. The MDX plugins were passed as imported functions:

```ts
// Before — works with webpack, fails under Turbopack
import rehypePrettyCode from 'rehype-pretty-code';
import remarkFrontmatter from 'remark-frontmatter';
import remarkMdxFrontmatter from 'remark-mdx-frontmatter';

const withMDX = createMDX({
  options: {
    remarkPlugins: [remarkFrontmatter, remarkMdxFrontmatter],
    rehypePlugins: [[rehypePrettyCode, { theme: 'one-dark-pro', keepBackground: true }]],
  },
});
```

Turbopack serializes loader options so it can hand them to its Rust-side pipeline. A function reference cannot be serialized. The fix is to name the plugins as **strings** and let the loader resolve them itself:

```ts
// After — plugin names as strings, options stay serializable
import createMDX from '@next/mdx';

const withMDX = createMDX({
  options: {
    remarkPlugins: [['remark-frontmatter'], ['remark-mdx-frontmatter']],
    rehypePlugins: [
      ['rehype-pretty-code', { theme: 'one-dark-pro', keepBackground: true }],
    ],
  },
});
```

The imports disappear entirely. If you have an MDX site and you're moving to 16, this is almost certainly the first thing you'll hit.

## What Broke #2: `next lint` Is Gone

`next lint` was removed in Next 16, and `next build` no longer runs ESLint at all. That's two changes, and the second one matters more than it looks: **if your only lint gate was the build, you no longer have a lint gate.**

The script change is trivial:

```json
{
  "scripts": {
    "lint": "eslint ."
  }
}
```

There's a codemod for it — `npx @next/codemod@latest next-lint-to-eslint-cli .` — but I did this by hand. The codemod rewrites your ESLint config toward an `eslint-config-next` template, and this repo has a long hand-written flat config built directly on `@next/eslint-plugin-next`. Letting a codemod near it would have caused more work than it saved. Read what a codemod does to *your* setup before running it.

Since `next build` no longer lints, the `eslint` block in `next.config.ts` is dead configuration and came out:

```ts
// Delete this — it only ever affected `next lint` and build-time linting
eslint: {
  dirs: ['src'],
},
```

### The Interesting Side Effect

`next lint` was scoped to `src/`. `eslint .` is not. Widening the scope surfaced **27 pre-existing warnings** in files that had never been linted — including `mdx-components.tsx`, which is real application code that defines every MDX component override on this blog.

They were all mechanical (formatting, prop sorting) and `--fix` handled them. But they'd been sitting there invisibly for months. The migration was an accidental audit.

## The Dependency Sweep, and Three Bumps I Refused

While I was in there I swept roughly thirty dependencies. Most were uneventful. Three were not, and all three are cases where "just take the latest version" would have been wrong.

### TypeScript 7 — blocked by a peer dependency

`pnpm outdated` offered TypeScript 7.0.2. But:

```json
// typescript-eslint@8.67.0
"peerDependencies": {
  "typescript": ">=4.8.4 <6.1.0"
}
```

Taking TypeScript 7 breaks linting outright. This isn't a judgement call — it's a declared incompatibility, and it's checkable in ten seconds with `npm view typescript-eslint peerDependencies`. TypeScript stays on 5.x until the ecosystem catches up. That's its own upgrade, on its own day.

### lucide-react 1.x — removed the brand icons

`lucide-react` went 0.577 → 1.32. The build then failed with:

```
Error: Export Github doesn't exist in target module
> 1 | import { Github, Linkedin, Twitter, LucideIcon } from 'lucide-react';
```

v1 removed the brand icons. Not renamed — removed. There are 6074 exports in the package and not one of them is a GitHub, LinkedIn, or Twitter mark. My footer social links use all three.

Replacing them means choosing new artwork, which is a design decision, not a dependency bump. So `lucide-react` stays on the 0.x line (bumped to the newest 0.577.0) and the brand icons keep working. A "sweep" that silently changes what your site looks like isn't a sweep.

### eslint-plugin-react-hooks 7 — a new rule with opinions

The v7 plugin adds `react-hooks/set-state-in-effect`, and it errors on two files here. One of them is this:

```tsx
const [mounted, setMounted] = useState(false);

useEffect(() => {
  setMounted(true);
}, []);

if (!mounted) return null;
```

That's the canonical `next-themes` hydration guard — the documented way to avoid a theme mismatch between server and client render. The rule is not wrong in general; calling `setState` in an effect body really does cause a cascading render. But rewriting a working hydration guard during a version upgrade is how you ship a subtle hydration bug.

So the rule is set to `warn`, with a comment naming both sites and why:

```js
// New in eslint-plugin-react-hooks v7. Fires on the next-themes hydration
// guard in ThemeSwitch and the mount-time sync in useScrollSpy, both of
// which are deliberate. Warn until those two are reworked.
'react-hooks/set-state-in-effect': 'warn',
```

A warning is a to-do with a location attached. Turning the rule off entirely would have thrown away the information.

## The Smaller Things

- **Node 20.9 is the floor.** Next 16 declares `"node": ">=20.9.0"`. I added a matching `engines` field so the constraint is visible in the repo rather than discovered on a deploy.
- **`next build` rewrites `tsconfig.json`.** It sets `"jsx": "react-jsx"` (mandatory — Next uses the React automatic runtime) and adds `.next/dev/types/**/*.ts` to `include`. It also reformats every array in the file, so run Prettier afterwards or your diff will be twenty lines of noise around two real changes.
- **`next dev` writes into `CLAUDE.md`.** Next 16 appends an agent-instructions block and logs `✓ Generated CLAUDE.md for AI agents`. Commit it or set `agentRules: false` in `next.config.ts` — otherwise every dev server run leaves your working tree dirty.
- **`next-env.d.ts` is generated.** ESLint 9+ flat config doesn't read `.gitignore`, so `eslint .` lints a file Next rewrites on every build. Add it to your config's `ignores` instead of fixing it forever.

## What We Actually Gained

- **Turbopack in production.** The dev server is ready in under 400ms, and static generation of 18 pages takes about 1.3 seconds. I did not run a rigorous before/after benchmark, so I'm not going to quote a speedup multiple at you — but the feel of it is not subtle.
- **React 19.2**, up from 19.1, alongside the React Server Components security patches that landed just before this upgrade.
- **A lint gate that covers the whole repo** rather than one directory — which, as above, immediately found things.
- **Shiki 4.** `rehype-pretty-code@0.14.5` already accepts `^4.0.0`, so this was a free major.

## How I Verified It

No test runner here, so verification is the build plus a browser:

1. `pnpm lint` — clean, 0 errors.
2. `pnpm build` — green. The page count reported 18 where Next 15 said 19, which looked alarming for about a minute. It wasn't: I diffed the emitted HTML against the registered slugs and all 13 posts were present. Next 16 just counts an internal entry differently. **Check the artifact, not the summary line.**
3. Every route in a headless browser at 1440px, in both light and dark, watching the console.
4. A specific assertion that Shiki highlighting survived — counting `data-rehype-pretty-code-figure` elements and coloured token spans in the built HTML. This is the thing most likely to break silently under a new bundler and least likely to be noticed by a smoke test.
5. A real commit, to confirm the upgraded commitlint 21 and lint-staged 17 still pass in the Husky hooks.

One trap worth naming: my first full-page screenshot showed the Experience timeline completely empty. It looked like the animation library major had broken it. It hadn't — the section uses `useInView` to reveal on scroll, and a full-page screenshot never scrolls, so everything off-screen stayed at `opacity: 0`. Scrolling to the section showed all entries at full opacity. If you use scroll-triggered animations, your screenshots will lie to you.
